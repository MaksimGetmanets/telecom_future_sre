# Замер MTTR: remediator на локальном стенде

Скрипт `chaos/mttr.py`, нагрузка 20 запросов/с. MTTR = время от внесения сбоя до 5 успешных проб подряд
(`GET /orders` через gateway быстрее 300 мс). Сырые данные: `mttr.csv`.

## Итог: с remediator (политики из `remediator/policies.yaml`, `DRY_RUN=false`)

| Сценарий | Сбой | Действие | Алерт, с | Действие, с | MTTR, с (3 прогона) | Медиана, с |
|---|---|---|---|---|---|---|
| errors | `errorRate=0.5` на orders | restart | 45–51 | 45–51 | 90 / 111 / 95 | 95 |
| latency | `delayMs=600` на orders | restart | 51–56 | 51–66 | 136 / 132 / 121 | 132 |

Алерт срабатывает за 45–56 с (`for: 30s` плюс интервал сбора метрик), действие ремедиатора следует сразу. Остальные
40–80 с уходят на перезапуск подов и подтверждение восстановления.

## Без remediator

В режиме `dry_run` (решение пишется в аудит, кластер не меняется) сбой не снимается: прогон errors завершился по
таймауту 600 с, `recovered=False`. Значит, без автоматики MTTR определяется временем реакции человека.

## Что мы выяснили по дороге

- **scale не лечит задержку из `fault.sh`.** Сбой хранится в памяти каждого пода, новые реплики здоровы, старые остаются
  медленными. С политикой scale latency-прогоны восстановились случайно (489 с) или не восстановились. Поэтому
  `DemoHighLatency` обрабатывается перезапуском, а scale оставлен для SLO-алертов Sloth по `orders`.
- **Защита от шторма действий работает:** лимит 6 действий в час на deployment остановил ремедиатор после серии
  прогонов (`skipped_guard`), максимум реплик 4 (`skipped_at_max`), алерты по gateway без политики
  (`skipped_no_policy`).
- **SLO-алерты Sloth** (окна до 6 ч) гаснут часами, перед прогоном ждём только алерты `Demo*`.

## Ограничения

- Стенд: WSL2 на ноутбуке, k6 и нагрузка в том же кластере, 2 реплики orders. Цифры верны для этого стенда.
- Одна серия из 3 прогонов на сценарий. Для медианы по 5+ прогонов запускайте с `--runs 5`.
- В `mttr.csv` остались прогоны, сделанные с неверной политикой scale и в dry-run, и один с остаточным SLO-алертом
  (`latency,2` от 14 окт: детект 1.2 с, это Burn-алерт от предыдущего прогона). В отчёт идут только строки с
  `recovered=True` после 14 окт 00:18 (latency) и серия errors 90 / 111 / 95.
